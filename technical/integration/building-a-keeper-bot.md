# Building a Keeper Bot

Keepers are permissionless bots that execute pending actions on the Zenex protocol in exchange for a share of trading fees. They fill limit orders when the market price reaches the user's limit, trigger stop-loss and take-profit exits, and liquidate positions whose equity has fallen below the maintenance threshold. Any Stellar address can operate a keeper. There is no registration, staking, or whitelist required.

## Economic Incentive

Keepers earn `caller_rate` (a configurable percentage, up to 50%) of the trading fees generated by each action they execute. Trading fees consist of the base fee plus the impact fee. On liquidations, the keeper also earns a share of the liquidation fee (the position's remaining equity). The `caller_rate` is a global parameter set in `TradingConfig`, and the same rate applies to all keeper actions.

At typical fee levels and position sizes, keeper profitability depends on the volume of actionable positions, the gas cost of submitting transactions on Stellar (which is very low), and competition from other keepers. The first valid transaction for a given position wins the fee.

## Architecture

A keeper bot follows a straightforward loop: monitor price feeds for changes, scan positions for actionable conditions, and submit batch transactions when conditions are met. The high-level architecture looks like this:

1. **Price monitoring.** Connect to Pyth Lazer (via the Zenex pricer service or directly) to receive real-time price updates for all supported trading pairs.

2. **Position scanning.** Maintain a local view of open positions by querying the trading contract's `get_user_positions` and `get_position` functions, or by consuming the Zenex API (`GET /positions/:address`) and indexer events. The indexer is more efficient for bulk scanning because it provides a pre-flattened view of all positions.

3. **Condition detection.** For each position, evaluate whether any keeper action applies given the current prices. The four conditions are: limit orders where the price has reached the limit, positions with equity below the liquidation threshold, positions whose stop-loss price has been triggered, and positions whose take-profit price has been triggered.

4. **Batch construction.** Group actionable positions into a batch. Obtain a fresh Pyth Lazer price payload covering all relevant feed IDs. Construct the `execute` call with the list of position IDs and the price data.

5. **Transaction submission.** Sign and submit the transaction to the Stellar network via Soroban RPC or the Zenex relayer at `https://relayer.zenithprotocols.com`.

## The Execute Interface

The trading contract exposes a single batch function for all keeper actions:

```
execute(caller: Address, requests: Vec<ExecuteRequest>, price_data: Bytes) -> Vec<u32>
```

The `caller` parameter is the address that receives the keeper fees. The `requests` vector contains one entry per position to process. The `price_data` parameter is a Pyth Lazer signed payload containing verified prices for all feed IDs referenced by the positions in the batch.

Price verification happens once at the start of the batch, amortizing the cost of the cross-contract call to the price verifier across all requests. Individual request failures return non-zero error codes in the result vector without aborting the batch, so a single invalid request does not cause the entire transaction to fail.

## Auto-Detection

The contract auto-detects the appropriate action for each position. For unfilled positions (pending limit orders), it attempts a limit fill. For filled positions, it checks conditions in priority order: liquidation first (equity below threshold), then stop-loss (price crossed SL level), then take-profit (price crossed TP level). This means keepers do not need to specify the action type per position. Simply submitting a position ID with current price data is sufficient, and the contract determines what to do.

## Condition Details

**Limit fill.** A pending limit order is fillable when the current price has reached or passed the user's specified entry price. For long limit orders, the current price must be at or below the limit price (`price <= entry_price`). For short limit orders, the current price must be at or above the limit price (`price >= entry_price`).

**Liquidation.** A filled position is liquidatable when its equity falls below the liquidation threshold:

$$
\text{equity} = \text{col} + \text{pnl} - \text{total\_fee}
$$

$$
\text{is\_liquidatable} = \text{equity} < \text{notional} \times \frac{\text{liq\_fee}}{\text{SCALAR\_7}}
$$

The `total_fee` includes all accrued funding and borrowing since the position was opened. A position can become liquidatable purely from fee accrual even if the underlying price has not moved.

**Stop-loss.** For longs, stop-loss triggers when `price <= sl`. For shorts, when `price >= sl`. The position must have `sl > 0` (SL enabled) and must have been open for at least `MIN_OPEN_TIME` (30 seconds).

**Take-profit.** For longs, take-profit triggers when `price >= tp`. For shorts, when `price <= tp`. Same `MIN_OPEN_TIME` requirement.

## Price Freshness

The price verifier enforces a `max_staleness` parameter on all submitted price data. If the price payload is too old, the entire batch will fail. Keepers must ensure they are submitting prices that are fresh at the time the transaction executes on-chain, not just at the time the transaction is constructed. On Stellar, block times are short (approximately 5 seconds), so the window between construction and execution is small, but keepers should account for occasional delays.

## Competition and MEV

Multiple keepers may detect the same actionable position simultaneously. Since Stellar processes transactions in order within a ledger, the first valid transaction wins the keeper fee for that position. Subsequent transactions targeting the same position will return a non-zero error code (position already filled, already closed, no longer liquidatable, etc.) but will not cause the batch to fail for other positions included in the same transaction.

There is no penalty for submitting a transaction that targets an already-processed position. The error is returned in the result vector and the gas cost is minimal on Stellar. Keepers should therefore err on the side of submitting optimistically rather than waiting to confirm conditions.

## Implementation Guidance

The `zenex-keeper` crate (Rust, tokio-based) provides a reference implementation of a keeper bot. It handles price feed subscription, position monitoring, condition evaluation, and batch transaction construction. Integrators building keepers in other languages should reference this crate for the correct condition evaluation logic and batch construction patterns.

For TypeScript-based keepers, the `zenex-sdk-js` SDK provides the `execute` method with typed request construction. Combined with a Pyth Lazer WebSocket connection for price data, this is sufficient to build a fully functional keeper in Node.js.

The recommended development flow for a new keeper is:

1. Set up a funded Stellar testnet account. You need XLM for transaction fees and optionally the collateral token for testing positions.
2. Connect to the Pyth Lazer price feed. The Zenex pricer service (`zenex-pricer`) provides a relay, or you can connect to Pyth Lazer directly.
3. Query the trading contract or indexer API for the list of open positions and pending limit orders.
4. Implement condition checks locally. Replicate the contract's condition logic (comparing prices to limits, computing approximate equity for liquidation checks) to filter positions before submitting.
5. Construct and submit `execute` batches. Start with small batches (5 to 10 positions) and increase as you gain confidence in your condition evaluation accuracy.
6. Monitor results. The return vector from `execute` tells you which positions succeeded and which failed. Use this feedback to tune your condition detection.

## Gas Costs

Stellar transaction fees are extremely low (fractions of a cent per transaction). The primary cost driver for keeper operations is the Soroban resource fees, which scale with the number of positions in a batch and the computational complexity of each action. Liquidations are slightly more expensive than fills because they involve more fee calculations. In practice, the keeper fee earned from a single successful action typically exceeds the gas cost of the entire batch by a wide margin.
